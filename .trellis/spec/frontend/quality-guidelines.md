# 质量规范

> 项目没有配置代码检查、格式化、类型检查或单元测试框架。质量依靠：与现有代码风格一致、关卡校验脚本、
> 生产构建和手动试玩。

---

## 代码风格（与现有文件一致）

- 两空格缩进、语句加分号、字符串用单引号、插值用模板字符串、多行字面量保留尾逗号。
- 相对导入必须写 `.js` 扩展名：`import { TILE } from './config.js';`。
- Phaser 以命名空间导入：`import * as Phaser from 'phaser';`，只在真正用到 `Phaser.*` 的文件中导入
  （各场景、`unitView.js`、`spellFx.js`、`saveMenu.js`）。
- 模块使用具名导出；`export default` 只用于关卡数组和 `extra_<组>.js` 对象。
- 项目习惯紧凑写法：短箭头函数、单行 `if (...) return ...;`、紧凑循环里用短变量名（`u`、`s`、`g`、`t`、`p`）。
  不要重新格式化相邻代码。
- 注释和所有面向玩家的文字都用**简体中文**；界面标签用全角空格做视觉间距（`'攻　击'`、`'胜　利'`）。
  与现有文件一样，在不直观的函数上方写一行简短的 `//` 注释。

## 必须遵守的写法

- `logic.js` 中的规则/公式保持纯函数，不依赖 Phaser（见 `directory-structure.md`）。
- `data.js` / `stages/*.js` / `characters*.js` 中的游戏数据必须能被 Node 导入，供校验脚本使用。
- 依赖动画结果的状态修改，必须先 await 动画完成（见 `scene-and-rendering.md`）。
- 新增的玩家/AI 行动类型要包在现有的 `try/catch` + `console.error` 保护中。
- 写入 registry 或存档快照时复制对象（`{ ...obj }`）。

## 禁止的写法

- 没有明确任务就新增依赖、框架、TypeScript 或构建插件。
- 二进制/图片素材：所有图形都是程序生成的。
- 各组并行编辑时，修改其他组的 `src/stages/<x>.js` 或 `extra_<x>.js`。
- 在已发布的关卡中重排现有 `events`（会破坏战斗中存档里的 `firedEvents` 下标）。
- 提交代码中残留 `console.log`（只保留现有的 `console.error`/`console.warn` 用法）。
- UI 销毁后，键盘/指针监听或补间仍在运行。

## 验证

```bash
node scripts/validate-stages.mjs          # 修改关卡/外形/数据后必须执行：0 错误
node scripts/validate-stages.mjs c        # 并行编辑关卡时只校验本组
npm run build                             # 提交整合后的改动前必须执行
npm run dev                               # 手动检查受影响的流程
```

- 手动试玩覆盖所有改动涉及的流程：移动、攻击/反击、策略/道具、对白与选项、事件/援军/单挑、
  胜利 → 下一关、败北 → 重新挑战、存档/读档（手动存档位 + 自动存档）、导出/导入。
- 各组并行编辑期间不要运行 `vite build`，完整构建留到整合阶段。
- 依赖说明：`package-lock.json` 被 git 忽略，所以 `AGENTS.md` 中的 `npm ci` 在新克隆的仓库上会失败；
  在此问题解决前请使用 `npm install`。

### 浏览器自动回归（57 关，每关两回合）

在预览浏览器里用 `window.game`（`main.js` 为调试暴露）写脚本驱动。已踩过的坑：

- **后台节流**：预览面板隐藏时浏览器暂停 rAF，定时器最快每秒一次。必须手动驱动循环，并放宽单帧时长上限，否则游戏时间几乎不走：
  ```js
  let last = performance.now();
  setInterval(() => { const n = performance.now(); game.step(n, Math.min(1000, n - last)); last = n; }, 16);
  ```
  再配合 `s.tweens.timeScale = s.time.timeScale = 10~15` 加速动画。
- **会阻塞流程的界面**：对白（`dialog.root.visible`）、选项（`dialog.choiceBox`）、整备界面（`s.modal` 为 true）、过关战果面板（`rewardPanel.js`，深度 3000）都会停住流程。回归脚本要用一个独立的定时器（约 50ms 一次）持续推进：推进对白、选第一个选项、点整备界面的“出阵”按钮（按 `label.text` 去掉空格后等于 `'出阵'` 查找；整备第一页的标签叫“阵容”，不会重名）、点战果面板的“确定”按钮（`'确定'`，或按 Enter）。剧情事件可能在我军行动中途弹出对白，只在两次行动之间推进对白的脚本会卡住。
- **整备卡片的点击区域**：`prep.js` 的“阵容”页（打开时的默认页）把所有卡片的元素平铺在同一个 `list` 容器里。要模拟点击某张卡片，先找到 22px 的名字文字，再取左上角坐标为 `(文字x − 104, 文字y − 10)` 的 `Zone`。不要取“同时包含名字和 Zone 的容器”的第一个 Zone，那是第一张卡片（曹操，锁定）。
- **切关时机**：`Battle` 场景实例在关卡间复用，停止场景不会取消上一关仍在等待的异步流程（AI 回合、阶段切换）。在敌军阶段中途停止并开下一关，残留流程会作用到新关卡，表现为每隔一关“离开战斗”、天气等状态串关。要等到 `turn >= 3 && phase === 'player' && state === 'idle'` 再切关；切关时先 `stop()` 全部场景，等 `game.scene.getScenes(true)` 为空，再 `start('Battle', { stage })`。
- **判读结果**：回归脚本不操作我军，所以需要保护单位的关卡（如 `xiandi`、`z_maicheng`）可能在第 2 回合判负。这类关卡要看布局判断玩家能否救援，不能直接当缺陷；判断能否打赢时，用 `planAI` 驱动我军完整对战。
  `over` 为 true 不一定是败北：例如汜水关友军击破华雄会直接胜利，要看最后一条日志和胜利条件。
- **改动能力、公式、射程后**：除回归外，还要对比“我军不行动 2 回合”时曹操 / 受保护单位的撤退率（新旧公式各跑数十局）。后期关卡站位按旧射程设计，射程或阶级变化会使能打到主将的敌人成倍增加，单击伤害看起来正常也会失衡。
- **重载**：修改 `src/` 会触发 Vite 整页重载，脚本状态全部丢失。长时间回归期间不要改代码；按 6~12 关一批运行，每批结束立刻读取结果。
  其他会话或子代理同时改工作区，也会让页面意外重载（读结果时报 `__all is not defined`）。所以每批结果要追加进一个累计数组（如 `window.__all`），并记下已完成的关卡下标；重载后从断点下标重装脚本、接着跑，不要从头重跑。
- **耗时判读**：预览面板隐藏时浏览器会节流，用 `game.loop.time` 估算的“正常速度每回合耗时”可能偏差数倍（曾把 62 秒误测成 488 秒）。发现异常值时先单独重跑该关确认；怀疑 AI 太慢时，直接在页面里对全部敌军调用一次 `planAI` 计时（正常为毫秒级），排除后再看动画。
- **分工**：57 关浏览器回归由主会话统一执行。子代理只做关键流程抽查，时间缩放设为 15，每关控制在 15 秒以内；子代理自己跑满 57 关会耗时 40 分钟以上。
- **记录项**：每关记录回合、阶段、是否结束、新增错误数（包装 `console.error`，并监听 `error` / `unhandledrejection`），整批结束后记录 `performance.memory.usedJSHeapSize`，确认内存不持续增长。
